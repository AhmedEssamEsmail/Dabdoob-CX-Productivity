### Goal
Remote coverage is inventoried, then a new migration schedules exactly the uncovered candidate routes — idempotent, settings-driven, secrets-free.

### Files
- Generated: `supabase/migrations/` | one output of `npx supabase migration new <name>` (record the filename in results before editing)
- Create: `specs/qa-live-sheets-freeze/results/S09-01-remote-cron.md` | evidence: remote cron.job snapshot + which candidates were skipped as already-covered

### Context
- `supabase/migrations/20261108231643_job_data_tick_pg_cron.sql:44-62` | THE pattern to copy: settings guard + `current_setting(...)` + `net.http_get` + unschedule-by-name DO guard
- `supabase/migrations/20261106201210_pg_cron_schedule.sql:82-184` | candidate job blocks + comments (schedules, mail-desk http_post header shape) — its {{APP_URL}}/{{CRON_SECRET}} placeholders are why it is DO-NOT-APPLY; do not reuse them
- `src/app/api/desk/job/mail/route.ts:6-15` | Bearer CRON_SECRET gate confirmed (WP-F18)
- `vercel.json` | none of the five candidate paths present (verified 2026-11-16)
- AGENTS.md remote rules | `env -u SUPABASE_ACCESS_TOKEN`, `--remote`, verify `Target:` line; remote WRITES need approval — the verify SELECTs are read-only

### Contract
Remote verify (read-only): `SELECT jobname,schedule,active FROM cron.job WHERE jobname LIKE 'cxh-%' ORDER BY jobname;` plus `SELECT current_setting('app.settings.app_url', true) IS NOT NULL AS url_set, current_setting('app.settings.cron_secret', true) IS NOT NULL AS secret_set;` (values themselves never printed). If cron schema is unreachable via the SQL path, escalate results file + NEEDS_USER rather than guessing. Migration content: `CREATE EXTENSION IF NOT EXISTS pg_cron/pg_net`; unschedule-by-name DO guard listing ONLY the jobs being scheduled; one `cron.schedule` per still-uncovered candidate using the settings-guard DO-block command (same shape as the applied data-tick file); mail-desk uses `net.http_post` with `'Content-Type','application/json'` + Bearer; every URL is `current_setting('app.settings.app_url',true) || '/api/...'` — no literals. Skip any candidate found already in cron.job (name it in the file comment + results). Timeout 60000 (30000 not needed — all five are heavy-ish GETs except mail-desk).
Out of scope: remote apply, vercel.json edits, health-check rows, scheduling routes outside the candidate list, exposing secrets in the file/results.

### Actions
1. Run the two remote verify SELECTs (`env -u SUPABASE_ACCESS_TOKEN npx supabase db execute --remote` or project MCP; confirm `Target:` = prod). Paste jobname/schedule/active rows (no secrets) into the results file.
2. `npx supabase migration new pg_cron_scoped_wave1` -> record filename.
3. Author the migration per contract: extensions, unschedule guard, one DO-guarded `cron.schedule` per uncovered candidate with its schedule string.
4. Header comment documents: scope rule (missing BOTH vercel + cron.job), the skip list observed remotely, WP-F18 mail-desk Bearer pre-req, apply path = `supabase db push` pending user approval, verification SQL block (copied from the data-tick file's footer).
5. `npx supabase migration list` registers the file.
6. Results file: remote snapshot + per-candidate scheduled/skipped verdict.

- Migration contains only uncovered candidates; zero secret literals; evidence file records remote state; migration list clean.
